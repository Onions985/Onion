上传图片超出大小限制时，可以降低编码质量，也可以缩小像素尺寸。两者影响不同，不应该隐藏在一个笼统的“压缩”按钮后面。PicAgent 的 iOS UploadImageCompressor 明确选择保持尺寸，用有限的 JPEG 质量阶梯寻找符合字节上限的结果。

## 一个有意保持窄职责的工具

该工具接收已完成业务裁剪或预处理的 UIImage，默认上限为 2×1024×1024 字节。源码没有在内部重新缩放图片，而是按预设质量序列尝试编码：

```swift
for quality in qualities {
    guard let data = image.jpegData(compressionQuality: quality) else {
        continue
    }

    if data.count <= maxBytes {
        return data
    }
}

return nil
```

质量从 0.82 逐步下降到 0.06，返回第一个满足限制的结果。它不会为了保证成功而偷偷改变长宽，也不会在仍然超限时返回最后一次数据。

## 尺寸没变，不代表视觉质量没变

保持像素尺寸可以保留裁剪后的几何关系，但 JPEG 质量很低时，文字边缘、渐变和细节仍会受影响。文件字节数满足后端限制，只说明传输条件通过，不等于图像适合所有业务用途。

头像、相册原图和文字截图可能需要不同质量策略。若产品要求最低可接受质量，应把它作为单独门禁；如果最低质量仍超限，再由用户或上层流程决定是否缩小尺寸、改用其他格式或拒绝上传。

这些属于后续产品设计建议，不是这段工具已经实现的功能。工具当前选择的是清楚的失败返回，而不是无条件生成某个输出。

## 为什么使用有限阶梯

固定阶梯让最多尝试次数可预期，也保留“尽量选择较高质量”的顺序。它不是在数学上搜索最佳压缩率，质量参数与文件大小之间也不应被假定为可以精确线性换算。

若改成二分搜索，需要定义迭代次数、候选保存方式和失败处理，并测量额外编码成本。对于小规模上传，有限阶梯可能已经足够，复杂算法不一定带来用户能感知的收益。

## 输出小，不代表处理内存小

UIImage 可能已经对应很大的解码位图。即使最后 JPEG 只有 2MB，编码过程仍需要处理原始像素和中间 Data，多次编码还会消耗 CPU。调用方应避免在主线程反复处理大图，并根据业务需要在更早的阶段控制输入尺寸。

这个函数同步返回 Data，没有负责线程调度、文件生命周期或上传重试。把它放到后台执行，并不意味着可以无限并发处理用户一次选中的所有大图，还需要上层资源预算。

## nil 应该对应清楚的用户反馈

输入尺寸不合法、maxBytes 非正、所有编码失败或最低质量仍超限，都可能返回 nil。若产品需要精确提示，可以把返回值扩展成受控错误类型，而不是让调用者猜测失败原因。

另外，JPEG 不保留透明通道，方向、色彩和元数据是否符合业务也要在完整图片管线中验证。不能因为这段函数名包含 upload，就认为它已经负责所有媒体规范化。

适合验证的素材包括文字截图、透明 PNG 转入、超大照片、渐变图和无效尺寸，并同时测量输出字节与视觉质量。压缩率与处理耗时会随素材和设备变化，需要分别测量。
