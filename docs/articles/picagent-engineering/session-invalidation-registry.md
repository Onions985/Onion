退出登录如果只删除 token，旧账号的内存状态、缓存观察者和迟到请求仍可能继续影响界面。另一方面，让认证模块直接依赖所有业务 Store，又容易形成循环依赖。PicAgent 鸿蒙端用一个小型失效注册表，把认证事件与具体业务清理分开。

## 注册表只认识同步回调

```typescript
export type SessionInvalidator = () => void

static register(key: string, invalidator: SessionInvalidator): void {
  if (key.trim().length === 0) {
    return
  }
  SessionInvalidationRegistry.invalidators.set(key, invalidator)
}
```

源码使用稳定 key 注册 process owner，同名注册直接替换，不会不断累积。注册表本身不依赖 Store、API 或 repository，因此认证层只调用这个基础边界，不需要知道每个业务模块如何清理。

这里对 key 只做空白检查，并没有把存储 key 自动 trim；调用方仍应使用约定好的稳定字符串，避免带空格的不同 key 被意外视为不同 owner。

## 为什么要求同步失效

接口注释明确禁止回调发网络请求或等待异步结果。同步失效的目标，是在账号切换边界立即关闭旧归属，让之后到达的异步结果无法继续写入。

真正的文件清理或耗时释放可以由各模块另行安排，但它们不能成为“旧会话是否已经失效”的前提。一个好的回调通常先推进本地 epoch、清空当前 owner，再触发可以安全延后完成的工作。

这属于使用建议；注册表不会强制检查回调内部是否偷偷启动网络调用，因此模块契约和审查仍然重要。

## 复制回调集合，再隔离异常

invalidateAll 先把当前 Map 中的回调复制到数组，再逐个执行。这样执行期间发生新的注册，也不会改变这一轮正在遍历的集合。

每个回调有独立 try/catch，一个模块清理抛错不会阻止其他模块失效。日志只记录通用失败信息，没有输出完整账号或业务状态。若需要定位具体 owner，可以在不泄露敏感数据的前提下加入稳定模块标识。

隔离异常不代表清理一定成功。需要关键状态失效的模块，应把核心 owner 变更放在尽量简单、不易失败的同步代码中，避免先执行复杂操作再清空归属。

## 生命周期范围决定注册方式

这份实现面向进程级 owner，没有提供 unregister。若把短生命周期页面对象捕获进静态 Map，就可能延长它们的寿命；稳定 key 替换也不能自动释放不同 key 注册的所有页面。

因此它适合少量长期模块，不应该直接成为通用页面事件总线。页面订阅需要自己的取消和释放机制，不能因为这里有一个回调表就把所有通知都接进来。

## 登出不是一次广播就完成

完整会话隔离还需要请求捕获会话代次、响应写入前复核、缓存按账号区分，以及数据库或本地文件的适当清理。注册表只是把同步失效动作集中触发，不会自动检查所有网络结果。

可以验证重复注册不增长数量、单个回调抛错不阻断后续、执行中注册的新回调不影响当前轮次，以及同账号重新登录也能触发新会话边界。这类小工具的价值，是把依赖关系拆开，同时给账号失效提供一个确定、可审查的发生点。
