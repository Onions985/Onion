做多个客户端，很容易把“一致”理解为每个按钮都在同一个位置、每张卡片都使用同样的尺寸。这样比较直观，也容易截图验收。但读完一次完整的业务接入，我更愿意先问：用户在不同端做同一件事，会不会得到相同的业务结果？

这不意味着视觉可以随意。它意味着一致性需要分层，最需要共同维护的部分，不一定是最容易被截图看到的部分。

## 先对齐用户得到的承诺

以 PicAgent 的签到为例，iOS 实现读取服务端的 `checkedInToday`、`directCheckinWillReset` 和 `makeupAvailableDayNumbers`。这些字段决定今天能不能签到、是否先确认重置，以及哪些日期允许补签。

如果 Android 显示可以补签，而 iOS 根据本地日期计算成不可补签，即使两个页面长得一样，用户体验仍然是不一致的。反过来，两个平台采用不同的 Sheet 和导航方式，但使用同一组准入规则，用户至少能理解产品承诺是什么。

我会把这类规则放在跨端对齐的第一层：可做的事、操作成本、失败含义和成功结果。

## 第二层是反馈的先后关系

这份 iOS 提交在签到成功后先使用 `balanceAfter` 更新会话余额，再发布钱包刷新事件，并展示当前页面的庆祝反馈。

这个顺序比“金币动画是不是同一个文件”更影响可信度。如果动画告诉用户成功，顶部余额却一直没变；或者当前页面失败，另一个页面已经展示增加的奖励，用户就需要自己猜测系统处于什么状态。

这里可以抽出一条对齐标准：不同端应该对同一个业务结果使用相容的反馈顺序。先确认什么、先展示什么、什么时候通知其他页面刷新，都属于产品行为。

## 原生实现可以有自己的边界

PicAgent iOS 的 Feature 通过 `CheckinProviding` 请求业务，由 DomainCenter 适配 KMP Repository，页面状态由 Swift ViewModel 管理。这条路径保留了共享服务能力，也给原生 UI 留出了自己的状态组织方式。

我不认为共享代码比例越高，就一定意味着架构越好。共享模型可以减少协议漂移，原生组件可以符合平台交互习惯；但为了消除最后一点代码差异，把导航栈、手势和生命周期都绑在一个抽象里，也可能让每个平台更难维护。

判断一个抽象是否值得保留，可以看它有没有减少需要同步的业务事实，而不是只看它删掉了多少行重复代码。

## 我会怎样安排跨端验收

| 先核对什么 | 要回答的问题 |
| --- | --- |
| 准入规则 | 同一账号、同一服务端状态，在各端能做的动作是否一致？ |
| 请求意图 | 重试、取消、重复点击是否仍代表同一件事？ |
| 成功语义 | 什么时刻更新余额、列表和详情？ |
| 失败恢复 | 原数据是否保留，用户能否理解下一步？ |
| 平台体验 | 导航、键盘、返回、字体和无障碍是否符合本端习惯？ |

这张表可以作为跨端接入时的验证清单。

## 页面数量之外，还要看行为能否解释

一个入口存在、一张截图相似、一个接口返回成功，分别只能说明局部事实。真正完整的功能需要它们在同一条用户流程里说得通。

我希望多端开发最终沉淀的是一套可解释的行为：用户知道自己做了什么，系统知道要记录什么，每个平台知道哪些部分应该保持一致，哪些部分应该用自己的方式表达。

这篇思考的事实起点是 `pic-agent-ios@1710e0d` 的 `CheckinProviding.swift`、`CheckinRootViewModel.swift` 和 `project/checkin.md`；关于优先级和验收顺序的部分是本文观点。
