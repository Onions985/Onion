一个接口主要在等待数据库和 HTTP 响应时，传统线程池往往先碰到线程数量上限。Java 21 的虚拟线程提供了更轻的等待方式，但把线程池换掉以后，数据库连接、下游吞吐和请求内存仍然有上限。理解这些独立的预算，比记住一个创建线程的 API 更有价值。

## 先区分吞吐和单次耗时

假设一次请求需要 20 毫秒计算和 180 毫秒等待，换成虚拟线程并不会自动把它变成 20 毫秒。收益来自同样的机器上可以承载更多处于等待状态的任务。若请求几乎一直占用 CPU，增加可运行任务只会加重调度竞争。

可以用一个估算辅助容量设计：平均在途请求数约等于每秒请求数乘平均响应时间。例如 300 次每秒、平均 0.2 秒，对应约 60 个在途请求。这只是稳定系统的平均关系，不能拿它代替峰值测量，也不能直接推导线程池应设为 60。

虚拟线程适合把业务代码保留为顺序结构。真正需要改变的是资源接纳的位置：线程便宜了，等待队列却不会因此免费。

## 把限制放在被保护的资源前

下面是 Java 21 的教学片段，省略 HTTP 客户端配置。`queryRemote` 必须自行配置网络超时；这里的信号量只保护下游并发。

```java
final class RemoteGateway {
    private final Semaphore permits = new Semaphore(32, true);

    String invoke() throws Exception {
        if (!permits.tryAcquire(150, TimeUnit.MILLISECONDS)) {
            throw new RejectedExecutionException("remote is busy");
        }
        try {
            return queryRemote();
        } finally {
            permits.release();
        }
    }
}

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> result = executor.submit(gateway::invoke);
    System.out.println(result.get());
}
```

32 和 150 都是示例值，应由下游容量、请求预算和压测确定。信号量应在调用方共享，不能每个请求新建一个。获取失败没有释放许可；成功获取后所有出口都经过 `finally`。如果获取过程被中断，应把中断或取消传回请求边界，而不是转成成功的空结果。

还需要入口限制。即使同时只有 32 个远程调用，数十万条等待许可的请求仍然可能占满内存。入口接纳、资源并发和请求截止时间解决的是三个问题，不能互相替代。

## 一个经常被忽略的连接池场景

假设数据库连接池有 20 个连接，服务允许 2000 个在途请求。若每条请求先拿数据库连接，再调用一个很慢的外部接口，20 个连接可能全部被远程等待占住。虚拟线程此时再多也无法让第 21 个数据库操作继续执行。

更合理的顺序通常是先完成必要的外部读取，再开启短事务校验和写入。如果业务必须跨越远程副作用，就应设计幂等、补偿或持久任务，而不是用一个长事务包住所有步骤。对于确实要求读写原子性的部分，保持连接持有时间可观测。

同理，不要把巨大请求体、图像字节和完整 ORM 实体挂在线程上下文中等很久。线程数量不是唯一内存指标，应一起观察在途请求数、许可等待数、堆占用和连接等待时间。

## 版本边界与排查顺序

本文以 JDK 21 为基线。该版本在某些 `synchronized` 和本地调用场景存在载体线程被固定的情况，可以结合 JFR 排查；不要把某个 JDK 版本的实现限制永久套用到所有后续版本。具体升级效果要在实际运行版本上复核。

我会按以下顺序评估迁移：先确认耗时主要来自等待；再为数据库、远程服务和 CPU 密集阶段分别划定预算；最后观察请求超时后资源是否真正释放。压测应保留相同业务数据、连接池大小和下游延迟，并记录吞吐、尾延迟及拒绝率。

一个方案如果吞吐增加，但下游错误率和超时后的在途任务持续增长，通常只是把原来的排队位置挪走了。虚拟线程的价值在于降低并发编程和等待成本，稳定性仍然来自明确的资源边界。
