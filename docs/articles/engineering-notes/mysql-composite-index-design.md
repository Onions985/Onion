联合索引不是把查询涉及的字段全部塞进去。它是一种有顺序的数据组织方式，需要同时考虑过滤、排序、返回字段和写入成本。设计索引前，我会先写出真实查询以及数据分布，再讨论字段顺序。

## 从一个文章列表查询开始

假设多作者系统按发布时间倒序显示已发布文章，同一时刻用 ID 稳定排序。下面是独立教学表的查询：

```sql
SELECT id, title, published_at
FROM article
WHERE author_id = :author_id
  AND status = 'PUBLISHED'
  AND published_at < :before
ORDER BY published_at DESC, id DESC
LIMIT 20;

CREATE INDEX idx_article_feed
ON article (author_id, status, published_at DESC, id DESC);
```

前两个等值条件确定一个连续分组，时间条件缩小范围，后两个字段对应结果顺序。这是一个值得验证的候选索引，不能仅凭 SQL 外形断言优化器一定采用它。若绝大多数记录都属于同一个作者，或者查询实际上没有作者条件，成本估计和适用性会变化。

MySQL 的联合索引能利用左侧连续前缀。`(author_id,status,published_at)` 对只按 `status` 搜索的页面，不等于有一个理想的 `status` 索引。即便某些版本和数据分布可以走其他优化路径，也不能把它当作设计时的默认保证。

## 范围之后的字段并非毫无作用

经常听到“遇到范围后索引就失效”，这句话容易混淆不同阶段。某些后续字段可能无法继续缩小同样的索引定位范围，但仍可能参与过滤、覆盖返回字段或满足排序。应结合具体执行计划看各阶段，而不是把整个索引判定成生效或失效两个状态。

同样，`Using filesort` 不意味着一定写磁盘，`Using index` 也不保证整体很快。一个覆盖索引如果扫描了大量无关行，仍然可能耗时；一个对少量结果做排序的计划可能完全可以接受。

## 覆盖索引的收益与代价

上面的查询返回 `title`，而索引没有包含它，通常还需要根据命中的记录取完整行。能否把标题也放进去？技术上可以评估，但长标题会放大索引体积，增加缓存压力，并让每次标题修改都更新索引。

我会先测列表实际返回的条数和回表成本。若每次只取 20 条，宽索引带来的写入和存储成本可能不划算。若是频繁扫描的大批量报表，覆盖的价值可能更高。不存在所有业务都应该覆盖的规则。

InnoDB 二级索引叶子记录还包含主键，主键设计同样会影响全部二级索引体积。不要只看新加的那几个字段而忽略整张表的成本。

## 用执行计划验证一个假设

推荐把验证拆为三步：先看估算计划，确认候选索引和过滤条件；再在可控环境执行 `EXPLAIN ANALYZE`；最后用接近真实的数据规模和冷热缓存条件测量实际查询。

```sql
EXPLAIN ANALYZE
SELECT id, title, published_at
FROM article
WHERE author_id = 42
  AND status = 'PUBLISHED'
ORDER BY published_at DESC, id DESC
LIMIT 20;
```

这里的 42 是演示参数，使用时应替换为实际测试条件。`EXPLAIN ANALYZE` 会实际执行查询，不能把它当作任意生产语句都可安全运行的静态解释器。观察实际行数、循环次数和估计偏差，比只看是否出现索引名更有用。

若同一条 SQL 对不同作者的表现差异很大，应检查数据倾斜、统计信息以及分页位置。测试只选一个数据很少的作者，容易得出过度乐观的结论。

## 索引也是需要维护的产品选择

每新增一个索引，都应能指向具体页面或任务。记录它服务的查询、预期扫描规模和可接受的写入代价。清理看似重复的索引前，也要核对唯一性约束、排序方向和其他查询的前缀需求。

示例使用 MySQL 8.0 已有能力，参考资料采用 8.4 手册。不同版本优化器细节可能变化，最终结论以实际环境的计划和测量为准。一个好的索引方案应该让查询路径可解释，也让未来维护者知道为什么要保留它。
