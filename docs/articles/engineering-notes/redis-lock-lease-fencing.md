分布式锁最危险的误解，是把“我曾经拿到锁”理解为“我现在仍然拥有写入权”。进程暂停、网络延迟和租约过期都可能让旧执行者继续工作。锁的释放写对了，只解决了其中一部分问题。

## 单实例租约的最小形状

对于可容忍相应故障边界的协调任务，可以使用随机令牌配合有期限的排他键。下面讨论单 Redis 实例，不把它包装成跨故障切换的完整一致性方案。

```text
SET lock:export:42 <unique-token> NX PX 10000
```

只有返回成功才开始执行。令牌要对每次获取唯一，不能只使用固定机器名。设置值、排他条件和过期必须是同一原子命令，不能先 `SETNX` 再单独 `PEXPIRE`，否则中间退出可能留下无期限锁。

释放时也不能无条件 `DEL`。假设 A 的锁已经过期，B 获取了同名锁，A 的迟到释放会误删 B 的锁。可以用脚本比较令牌后删除：

```lua
local current = redis.call('GET', KEYS[1])
if current == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

脚本适用于常见 Redis Lua 能力，不依赖某个新版本的扩展命令。它保护的是锁键归属，不保证业务写入本身安全。

## 租约过期之后的旧执行者

设想 A 获取 10 秒租约，执行到第 3 秒发生长暂停；租约过期后 B 获取锁并完成导出；A 恢复后仍然把旧结果写到“最新导出”位置。A 最后即使正确地发现自己不能删除 B 的锁，旧结果也已经覆盖了新结果。

续租可以降低这类情况的发生概率，却不能保证进程永远及时续租。是否还有锁不能只在最后检查一次，因为检查与写入之间也可以失去租约。真正需要保护的是下游副作用的接纳点。

## Fencing token 应由资源端检查

一种设计是每次合法获取工作权时分配递增代次，写入资源时携带代次，资源端拒绝旧代次。关键是单调性来源可信，而且比较与写入原子完成。

```sql
UPDATE export_slot
SET object_key = :new_object,
    last_fence = :fence
WHERE id = :slot_id AND last_fence < :fence;
```

这个简化例子假设槽位已存在、一个代次只提交一次最终结果，且发号与任务所有权协议可靠。相同代次的幂等重放需要另加请求身份和结果一致性判断。不能随便拿一个可能在故障恢复后倒退的计数器，就宣称完整 fencing 已经成立。

如果下游是不可条件写入的第三方接口，还需要幂等键、版本化对象名、最终指针交换或补偿等机制。给请求加一个字段，却没有服务端拒绝规则，不会产生保护效果。

## 什么时候根本不需要分布式锁

若只是防止同一订单重复创建，数据库唯一键通常更直接；若是库存条件扣减，可以使用条件更新；若是减少重复缓存回源，进程内合并可能已经足够。它们把约束放在事实发生的位置，恢复路径往往也更简单。

分布式锁适合解决跨执行者协调，但不应替代业务幂等。一个任务可能在响应丢失后被重试，也可能在故障恢复时重新领取；即使任意时刻只有一个执行者，同一副作用仍可能在不同时间执行两次。

评估时应明确：允许重复工作的代价、锁服务失联时是否继续、执行最长时间、续租失败如何退出、旧执行者如何被下游拒绝。官方 Redis 锁文档也专门提醒长任务的 fencing 与时钟假设。理解这些边界以后，才能判断一个简洁的租约是否足够，而不是被“已经加锁”四个字安慰。
