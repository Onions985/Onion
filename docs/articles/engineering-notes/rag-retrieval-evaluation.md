RAG 演示通常从“把文档切块、转向量、检索后交给模型”开始。真正要让它可靠回答问题，需要知道失败发生在哪一层：资料根本不存在、检索没找到、上下文被截断，还是模型忽略证据。只看最终答案是否流畅，无法指导改进。

## 先把资料变成可追踪的证据

每个片段除了文本，还应保存文档身份、来源版本、章节路径和权限范围。示意结构如下：

```json
{
  "documentId": "guide-42",
  "sourceVersion": "rev-8",
  "chunkId": "guide-42:rev-8:section-3:chunk-2",
  "section": ["部署", "数据库迁移"],
  "accessScope": "engineering",
  "text": "示例正文，不代表真实业务资料"
}
```

切块长度不是唯一参数。表格、代码、标题和前置条件可能需要一起保留；把“仅适用于测试环境”切到另一块，检索结果即使字面相关，也可能失去关键限制。

文档更新后，应能够定位并替换旧版本片段。若只不断追加新向量，不清理或隔离旧版本，系统可能同时引用两套互相冲突的操作步骤。

## 检索评价和回答评价分开做

可以先准备一组人工核对的问题，每个问题标记所需证据片段集合，再看 top-k 是否覆盖这些证据。简单的片段召回率定义为命中的必要证据数除以必要证据总数，但证据如何标注、同义片段是否算命中，都需要统一规则。

```python
def recall_at_k(expected: set[str], ranked: list[str], k: int) -> float:
    if not expected:
        raise ValueError("answerable questions need evidence labels")
    found = set(ranked[:k])
    return len(expected & found) / len(expected)
```

这个函数演示了评价指标的计算方式。对于资料中不存在答案的问题，应单独评价拒答能力，不能把空证据集合随意记为满分。

检索命中之后，再检查回答是否覆盖问题、是否有证据支持、引用是否指向正确版本、是否加入资料之外的断言。检索召回高但回答差，应检查上下文组织与生成约束；检索就没找到证据，则应先调整检索层。

## 关键词和语义检索各有盲点

错误码、类名、接口路径等精确词，常常适合保留词法检索通道；自然语言改写则可能受益于语义检索。可以把两路结果按明确策略合并，再重排和去重，但是否优于单路，需要同一评价集验证。

不要为了增加召回无限扩大 k。上下文预算有限，大量相似片段会挤掉补充证据，也可能增加冲突。可以按文档和章节做适当多样化，保留来源与时间信息，让模型知道哪些片段属于同一版本。

重排成本也要计入延迟与预算。一个离线评价提高一点、在线耗时翻倍的方案，未必符合用户场景。结果质量、延迟、费用和权限正确性应该共同进入选择。

## 权限必须在证据进入上下文前生效

检索到内部文档后，再让模型“不要泄露”，不能代替权限过滤。用户只应该检索或获取自己被授权的片段。权限变化时，缓存键、向量索引元数据和引用下载入口都需要相应处理。

文档正文也可能包含指令式文本。系统应把它当作待引用资料，而不是新的控制命令；涉及外部工具和数据写入时，授权不能由检索片段决定。引用格式清楚，有助于把答案和资料来源区分开。

## 建立一个能解释变化的评价闭环

我会把问题按精确查找、多段综合、版本冲突、无答案和权限边界分类。每次只改变切块、检索、重排或提示中的一个主要变量，保存索引版本、模型配置和输入证据，避免结果变化后无法归因。

失败样本比平均分更有启发：某个类名总是找不到，可能是词法通道缺失；新旧文档混引，可能是版本管理；答非所问但引用正确，可能是问题拆解。评价不只是选模型，也是检查整个资料处理链路。

RAG 原始论文提供了检索与生成结合的研究背景。本文的权限、版本与评价拆分属于工程设计建议，不把论文中的实验结论直接套到个人知识库，也不承诺向量化之后就不会产生错误回答。
