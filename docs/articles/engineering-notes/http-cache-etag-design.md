浏览器缓存、CDN 和接口缓存经常被混成一个概念。设计 HTTP 缓存时，需要分别回答：谁可以保存响应、保存多久、什么时候必须询问服务器、询问后是否还需要传正文。`Cache-Control` 与验证器分别承担这些职责。

## 三种常见指令不要混用

`no-store` 要求缓存不要存储该响应；`no-cache` 允许保存，但再次使用前需要成功验证；`private` 限制共享缓存存储，浏览器私有缓存仍可能使用。它们不是“缓存强度从高到低”的三个等级。

例如公开文章可以设置短暂新鲜期，并通过 ETag 验证；登录后的个人资料若允许浏览器保存，可考虑私有、每次验证；包含敏感临时凭据的响应则更适合禁止存储。具体策略还要结合授权方式和 CDN 配置，不能只在应用代码里加一行就假定所有中间层都会按预期工作。

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=60
ETag: "article-812-r7-zh"
Content-Type: application/json; charset=utf-8
```

这组头是教学示例。60 秒意味着在符合规则时可以直接复用一段时间；它不表示所有用户一定在 60 秒后看到最新内容，也不包含应用内存缓存的刷新承诺。

## 条件请求节省的是正文传输

缓存变旧后，客户端可以带上 `If-None-Match`。服务端确认所选表示仍相同，就返回 304，无需再传同一正文。

```http
GET /articles/812 HTTP/1.1
If-None-Match: "article-812-r7-zh"
```

若文章已更新到 r8，应返回新正文与新 ETag。服务端仍需要进行路由、权限判断和版本判断，所以 304 不等于请求完全没有成本。把 ETag 生成方式设计为可以快速读取的内容版本，往往比每次完整渲染后重新哈希更划算。

强验证器应随着所选表示字节变化而变化。若内容经过不同压缩、语言转换或模板变化，同一个版本号未必足以代表完全相同字节。需要根据实际表示生成验证器，或使用符合语义的弱验证器，并理解它的适用限制。

## 语言、身份和 Vary

如果同一个 URL 按 `Accept-Language` 返回不同语言，应让缓存区分相应请求头；如果语言已经在 URL 路径中，通常可以直接由 URL 区分。`Vary` 描述选择响应所依赖的请求头，不能把它当成自动授权机制。

对用户资料，最容易犯的错误是把经过认证的响应标为公共缓存，却没有正确隔离身份。更稳妥的起点是明确私有或禁止存储，再根据产品需求和基础设施逐步优化。退出登录后还需要处理应用状态与本地数据，HTTP 缓存指令不能清理所有其他存储。

CDN 是否缓存带 Cookie 的请求、是否覆盖源站头、是否忽略部分查询参数，都应该用实际请求验证。不能只看浏览器开发工具里的一次 304 就推断整条链路正确。

## 版本化静态资源与可编辑内容

带内容哈希的脚本或样式文件可以采用较长缓存期，因为更新会得到新 URL；HTML 入口通常需要更短的生命周期，才能及时引用新资源。文章正文可编辑，若 URL 不变，就需要短新鲜期或验证机制。

删除或撤回内容也要进入设计。已经被允许缓存一年的公开正文，服务器随后返回 404，并不意味着所有新鲜缓存都会立刻回源。撤回时效是业务要求，应反过来限制缓存策略，必要时使用可执行的失效流程。

我会用首次请求、仍新鲜、过期未修改、过期已修改、语言变化、账号变化六条路径验证缓存。记录状态码、Age、ETag、Cache-Control 和实际响应体来源。本文依据 RFC 9111 讨论通用语义，具体浏览器与代理的组合仍需在部署环境里检查。
