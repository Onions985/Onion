缓存旁路模式很常见：先查 Redis，未命中再查数据库，最后把结果放回缓存。真正麻烦的地方不是这三行代码，而是读写交错、过期策略和故障恢复。缓存是否允许短时间过时，应该在设计之初就说清楚。

## 先画出一个旧值回填窗口

假设缓存为空。请求 A 查询数据库，拿到旧资料后暂时停住；请求 B 更新数据库并删除缓存；A 随后恢复，把旧资料重新写回 Redis。此时数据库已经是新值，缓存却又出现了旧值。

这个时间线说明，“更新数据库后删除缓存”有实用价值，但不能被称为无条件强一致。延迟再删一次能缩小部分窗口，也依赖延迟选择、消息可靠性和任务执行；它不是数学上消除所有交错的开关。

如果业务是公开资料页，允许几十秒内收敛可能可以接受；如果是支付额度或实时权限，就不应把同一套缓存承诺直接套上去。先定义允许过时多久、哪些操作必须回源，再决定实现。

## 缓存内容应有版本语义

一个教学用缓存条目可以包含业务版本和数据，而不是只存裸 JSON：

```json
{
  "schemaVersion": 1,
  "entityVersion": 18,
  "cachedAt": "2024-03-12T08:00:00Z",
  "value": { "displayName": "Example" }
}
```

业务版本来自数据库的受控更新，不能简单使用各应用机器的当前时间替代。版本比较可以阻止已知旧值覆盖已知新值，但如果新版本缓存已经被删除，单个缓存键就没有东西可比较了。要提供更强保证，可能需要额外的版本水位、可靠失效事件或直接绕过缓存。

因此“加一个 version 字段”只是提供比较材料。比较在哪里原子执行、水位存多久、Redis 故障后如何恢复，才构成完整协议。

## 过期、空值与热点需要不同策略

给 TTL 加适量随机抖动，可以分散同一批键同时过期带来的回源峰值。Redis 的 `SET` 支持将写值与过期设置放在一次命令中，避免写成功但单独设置过期失败而产生永久缓存。

```text
SET profile:42 <serialized-value> EX 75
```

这里的 42 和 75 都是示例。缓存空结果时应使用明确的空值标记与较短生命周期，区分“确认不存在”和“数据库临时异常”。把错误缓存成不存在，会把短故障变成长期错误页面。

热点键过期时，进程内 single-flight 能让同一实例的并发读共享一次回源；多实例仍可能各发一次。是否需要跨实例协调，要根据回源成本和容量决定。不能为了省一次便宜查询就引入复杂的分布式锁。

对于允许陈旧读取的内容，可以返回带年龄的旧值并后台刷新；对于权限或用户隔离数据，应谨慎设计，保证缓存键包含正确租户和身份范围，且授权判定不依赖一个过期展示快照。

## 故障降级不能把数据库压垮

Redis 连接失败后直接让全部流量回源，可能把缓存故障放大成数据库故障。回源也应有并发限制、超时和适当的拒绝策略。观察数据库是否有能力承担完全无缓存的流量，比一味追求缓存命中率更接近容量规划。

我会分别记录命中、正常未命中、缓存错误、陈旧返回、回源失败和回填失败。一个 99% 的命中率可能仍然掩盖最热门数据持续过时；只看命中率无法评价一致性。

验证可以用可控制暂停点的测试制造“读旧值—写新值—旧值回填”交错，再确认实际收敛机制。不要仅靠压力测试碰运气。这套缓存策略不提供跨节点线性一致性；缓存越接近核心业务不变量，越需要明确它究竟是加速层还是事实来源。

## 给一致性承诺一个可观察的期限

假设产品允许资料更新后最多一分钟收敛，就应把写入事件延迟、缓存 TTL、重试退避和页面本地缓存一起计入，而不是只把 Redis TTL 设成一分钟。页面如果自己永久保存旧响应，服务端已经收敛也没有意义。可以在响应里携带业务版本，在更新成功后主动刷新相关视图，并用定期抽样比较缓存版本与数据库版本。若无法保证一个严格上限，应把它表述成正常情况下的收敛目标，记录超出目标的样本并分析原因，而不是对外承诺不存在的强保证。
