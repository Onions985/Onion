列表的第一页很快，翻到后面越来越慢，常见原因是偏移分页要求数据库先找到并跳过大量记录。游标分页把问题改成“从上一次看到的位置继续往后”，但要设计正确，必须先定义稳定顺序和数据变化时的产品语义。

## 两个字段共同确定位置

如果文章按发布时间倒序排列，单独保存时间不足以标识位置。同一毫秒可能发布多条记录，因此再加入唯一 ID 作为平局裁决字段。

```sql
SELECT id, title, published_at
FROM article
WHERE status = 'PUBLISHED'
  AND (
    published_at < :cursor_time
    OR (published_at = :cursor_time AND id < :cursor_id)
  )
ORDER BY published_at DESC, id DESC
LIMIT 21;
```

页面展示 20 条，额外取一条判断是否还有下一页。下一页游标来自实际展示的第 20 条，而不是多取出的第 21 条，否则会漏掉那条记录。首屏没有游标，应使用独立的查询分支，避免拼出含糊的空值比较。

可评估的索引是 `(status,published_at DESC,id DESC)`。是否实现预期范围扫描仍应观察执行计划。游标分页改善的是定位方式，不会自动解决复杂关联、低选择性过滤或巨大正文回表的成本。

## 游标应该携带查询上下文

假设用户先看 Java 标签，拿到了游标，随后切换到 Python。若把旧游标原样带过去，会从 Python 列表中间开始。客户端应在过滤条件变化时清空游标，服务端也可以把过滤摘要编码进游标进行校验。

```json
{
  "v": 1,
  "time": "2023-06-18T09:20:00.123Z",
  "id": "812",
  "filter": "tag:java;status:published"
}
```

这只是结构示意。生产接口可以把它编码并签名，使客户端不能任意修改查询边界；Base64 只是编码，不提供防篡改能力。即使有签名，每次请求仍然要重新检查权限，不能把游标当成访问令牌。

跨 JavaScript 边界时，大整数 ID 应采用字符串，避免精度损失。时间精度也需要与数据库字段保持一致：数据库存毫秒，客户端若只保留秒，边界就变了。游标格式应有版本号，方便以后迁移排序字段。

## 数据变化以后，什么叫正确

新文章插入到当前游标之前，继续向后翻不会看到它，通常符合“继续阅读旧内容”的预期。用户刷新首屏后再看到新文章。删除旧文章会使下一页变短，但不应导致已经看过的项目因为位置偏移而重新出现。

如果排序字段可修改，例如文章重新发布后改变时间，记录可能跨越游标边界，导致一次遍历中重复或遗漏。游标不是数据库快照。需要完整稳定导出的任务，应使用专门快照、固定数据版本或其他可证明的读取方案。

仅增加 `published_at <= first_page_time` 可以挡住一部分新增数据，却不能阻止已有记录被编辑，也不能自动处理删除。是否允许这些变化，应先写成产品规则，再决定技术复杂度。

## 反向翻页和跳页是不同需求

向前翻页需要反转比较方向和排序，取出结果后再恢复展示顺序，不能简单把 `<` 换成 `>` 而保留所有其他逻辑。尤其多个排序字段混合升降序时，需要按词典序逐项设计比较条件。

任意跳到第 500 页则不是游标擅长的操作。后台管理的小数据列表可能继续使用偏移分页更省事；信息流和连续阅读适合游标；大规模导出应使用任务和检查点。没有必要为所有页面统一一种分页 API。

验证时至少准备同时间多条记录、空页、刚好一页、末页不足、过滤切换、删除边界记录和排序字段变化几组数据。观察结果序列是否符合承诺，比只检查接口返回了 `nextCursor` 更重要。实际收益取决于索引、页深和数据分布。
