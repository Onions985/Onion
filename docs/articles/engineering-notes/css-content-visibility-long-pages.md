长文章归档页可能只有几十张卡片，却包含复杂排版、代码高亮和图片。优化前需要知道成本发生在下载、脚本执行、布局还是绘制。`content-visibility` 能帮助浏览器跳过暂时不需要的离屏渲染工作，但不会让 DOM、数据和 JavaScript 自动消失。

## 按内容区块建立边界

对于相互独立的归档区块，可以尝试以下渐进增强：

```css
.archive-section {
  margin-block: 2rem;
}

@supports (content-visibility: auto) {
  .archive-section {
    content-visibility: auto;
    contain-intrinsic-size: auto 36rem;
  }
}

@media print {
  .archive-section {
    content-visibility: visible;
    contain-intrinsic-size: none;
  }
}
```

估算尺寸的作用是为尚未完整渲染的内容保留空间，减少滚动条和布局的突然变化。36rem 是演示值，应根据区块实际高度分布选择。文章正文、短卡片和图片瀑布流不适合共用同一个估计。

`auto` 让浏览器根据相关性决定跳过的工作，并保留内容的文档语义。它与 `display:none` 的目标不同，也不是把所有屏幕外内容永久隐藏。不要为了视觉省事再统一加上 `aria-hidden`，那会改变辅助技术能否访问内容。

## 它和虚拟列表解决的问题不同

虚拟列表通常只挂载视口附近的一部分项目，因此能够减少 DOM 数量，但会带来焦点、定位、页面查找和动态高度管理等额外问题。`content-visibility` 保留 DOM，使用成本更低，却无法解决十万条记录本身占用的大量内存。

可以按规模选择：几十个独立区块先看渲染跳过是否足够；数千条复杂交互项目评估虚拟化；更大的内容集合优先考虑分页和产品上的信息组织。不要因为某个属性很方便就把全部数据一次加载进来。

图片仍需设置合适尺寸与加载策略。浏览器跳过部分布局绘制，不等于网络资源必然不会下载。代码高亮若在脚本里主动遍历全页，相关 CPU 开销也可能照样发生，需要单独设计初始化时机。

## 不要用测量抵消浏览器的跳过机会

如果滚动事件中不断读取所有区块的尺寸，再写回样式，可能触发额外布局工作。可以先考虑 IntersectionObserver、CSS 或局部测量，避免每一帧都查询整个文档。

例如只需要在内容进入视口时淡入，观察是否相交就足够，没有必要每帧计算每个元素的精确距离。动画应独立考虑减少动态效果偏好，且初始样式不能让脚本失败时正文永远透明。

粘性定位、浮层和跨区块定位也需要实测。渲染包含边界可能影响原先依赖祖先关系的效果，不能在整个页面根节点上随意套用后就认为所有布局都等价。

## 测量应该对准实际症状

先固定同一份长页面、浏览器版本和设备条件，分别观察初次渲染、快速滚动和返回已看区块。记录布局与绘制耗时、长任务、布局偏移和内存，而不只看一个总加载时间。

如果初次卡顿主要来自解析大段 Markdown，CSS 属性不会消除这部分脚本工作；如果主要来自图片解码，也要优化图片尺寸和格式。只有找到成本归属，才能解释为什么某个改动有效。

还需要人工检查键盘 Tab 顺序、锚点跳转、页面查找、打印和屏幕阅读器。MDN 提醒离屏内容仍与可访问性树有关，区块内部本来需要隐藏的元素也应正确管理自身语义，不能只依赖父区块暂时未绘制。

实际项目仍应对目标浏览器做能力检测和回归，保留不支持时的正常布局。这个优化最适合已经语义正确、结构清楚的长页面，而不是用来掩盖一次性加载过多内容的问题。
