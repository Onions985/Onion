## 一个查询模块，为什么值得单独拆出来

微服务最难的部分通常不是创建另一个 Spring Boot 启动类，而是回答：这个进程离开主应用以后，还需要带走多少业务知识？

PicAgent 的话题目录是一个比较明确的切入点。它负责提供可用话题、分页列表和单条详情；管理端仍然维护目录，群聊、钱包与消息也有各自的事务。查询目录没有必要加载整个群聊运行环境。这使它适合用来检验服务边界，而不是借一次拆分重写所有业务。

我把这次调整理解为三个分离：契约与实现分离、外部路由与业务执行分离，以及查询责任与管理写入责任分离。

## contract 应当小到可以说清全部内容

这一阶段增加了 `agent-topic-catalog-contract` 和 `agent-topic-catalog-service`。前者是普通 JAR，包含内部 HTTP 接口、小型返回模型与协议常量；后者才是运行服务。

一个看似方便的捷径，是让主应用直接依赖新服务的代码。这样编译很快通过，运行边界却仍然模糊：调用方随时可以碰到 Mapper、实体和实现。这里选择只共享 contract，避免应用之间通过类路径形成隐性耦合。

同样，公共响应外壳可以进入公共库，话题分页上限则仍属于话题契约。两者的区别是变化原因：所有服务都需要理解响应结构，不代表所有服务都需要理解话题规则。

## 网关不应该成为另一个业务服务

同一提交里的最终形态已经让公共目录请求直接经网关进入目录服务；早期“主服务代理一次内部查询”的设计是过渡方案，不能当作最后的调用链。

目录路由优先匹配 `/api/topicGroup/catalog` 及其子路径，其他 `/api/**` 请求继续进入主服务。保留完整路径的意义在于：一个未知目录子路径不应意外落回主服务，变成难以定位的另一种行为。

网关里的凭证过滤器有这样一段实际代码：

```kotlin
val route = exchange.getAttribute<Route>(GATEWAY_ROUTE_ATTR)
if (route?.id != GatewayProtocol.TOPIC_ROUTE_ID) return chain.filter(exchange)
val request = exchange.request.mutate()
    .header(TopicCatalogProtocol.SERVICE_KEY_HEADER, properties.serviceKey).build()
return chain.filter(exchange.mutate().request(request).build())
```

这段代码只给目录路由加入服务凭证。完整链路还有前置边界过滤器，负责清除外部伪造的内部头。单独复制上述片段并不能构成完整鉴权。

目录服务同时验证网关服务身份和原用户 JWT、会话状态。前者回答请求是否来自允许的内部入口，后者回答用户是否仍处于有效登录状态，不能互相替代。

## 拆了进程，数据边界仍可以是过渡状态

这一阶段目录查询仍读取同一张业务表，管理写入保留在主服务。准确的描述是“查询服务拆分”，而不是“目录已经拥有完全独立的数据系统”。

这种选择有现实价值：它让查询进程先独立运行，同时避免为了拆分而引入新的同步协议。但代价也要承认：表结构变化仍需要两个服务协调，数据库故障仍可能同时影响它们。独立进程只是隔离的一部分。

查询侧只筛选启用条目，按既定顺序分页，并用多取一条判断下一页。将只读责任限定清楚，比预先增加缓存、消息同步和额外状态更容易验证。

## 失败要保留它本来的含义

目录服务不可用时，网关返回明确的 503，不回退成成功空列表，也不悄悄改为主服务查库。

空列表表示“查询成功，目前没有条目”；503 表示“这次查询没有得到可信结果”。如果把二者合并，页面虽然少显示一次错误，用户却可能误以为内容被清空，监控也丢失故障证据。

连接和响应等待有各自上限，目录路由不做应用层重试。这不是说重试永远不好，而是这一条读取链路首先需要明确的耗时与失败边界，再决定是否增加恢复策略。

## 我会怎样评估这次拆分

我更关心这些问题：主服务停止时目录查询还能否独立执行？目录停止时是否准确失败？请求有没有偷偷经过主服务？公共响应是否保持兼容？内部运维路径是否意外暴露？

这些问题比“现在有几个服务”更能衡量拆分结果。隔离测试之后，还需要连接实际数据库、Redis、登录服务和移动端，验证完整的调用链。

架构的价值在于让变化与故障有清楚的落点。对这个阶段而言，把一条查询链路拆得可解释，比一次性画出庞大的服务地图更有用。
