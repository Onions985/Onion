## 页面需要的是用途，不一定是像素参数

头像列表、内容卡片和详情查看都展示图片，但它们不需要相同的体积与清晰度。如果每个页面自行拼接缩放、格式、质量参数，最初很灵活，后来就难以知道哪些图片为什么这么大，哪些页面又在重复处理同一张图。

PicAgent 在共享层增加语义档位，把页面的选择收敛为用途：

```kotlin
enum class ImageVariant {
    THUMBNAIL,
    CARD,
    DETAIL,
    MASTER,
}
```

这些是源码中的真实枚举值。调用方表达“这里是卡片”，共享策略再映射到具体变体。将来调整卡片清晰度时，可以修改集中策略，而不必逐页寻找字符串。

## 把技术值集中，并不意味着所有图片都能处理

该版本给缩略图、卡片、详情配置了不同缩放边界与 WebP 质量，MASTER 保留原始结果。但这些参数只适用于允许处理的自有 OSS 地址或 legacy object key。

外部图片、预签名地址、已经带有处理参数的地址都需要特别对待。给任意 URL 追加 `x-oss-process`，可能让第三方服务拒绝请求；修改签名 URL，也可能破坏它的访问合同。

源码在构造变体之前有这一段判断：

```kotlin
if (eligibleUrl.hasProtectedOssQuery()) {
    return eligibleUrl
}

return eligibleUrl.appendOssProcess(variant.ossProcess())
```

这里之前已经完成地址资格检查。单独复制最后一行并不能得到同等行为；真正值得复用的是包含资格判断的完整能力。

## URL 不是可以随便拼接的一行文字

实现中区分了 authority、query 和 fragment，保护签名相关参数与已有处理参数，再决定应该用问号还是连接符追加参数。

这些细节没有视觉上的存在感，却决定边缘地址是否还能打开。尤其当图片来自分享、生成任务或私有媒体时，同一个字段可能承载不同访问策略，不能只根据“看起来像图片链接”就做同一种处理。

该方法也保留旧的无参数扩展，减少对既有调用方的影响。兼容层应该有清楚的适用范围，而不应成为所有新图片合同的默认加工站。

## 服务端已交付变体，就直接消费变体

源码注释明确指出：当服务端已经返回 `ImageDeliveryUrls`，客户端应直接使用对应 URL，不再调用这个 legacy 转换方法。

这条界线很重要。一个集中方法再好，也不该覆盖服务端已经决定的资源版本、权限和处理方式。否则客户端会在另一层重复加工，最终没人能解释用户真正加载的是哪张图片。

因此，可以同时存在两条清楚的路径：旧资源由受控兼容方法生成展示 URL；新资源消费服务端提供的展示地址。两者的目的都是集中策略，权威来源却不同。

## 我更在意收益能不能测出来

选择较小变体通常是减少传输体积的一种手段，但具体能节省多少，依赖原图、处理结果、缓存命中和页面布局。不能仅凭枚举存在就写出一个百分比。

真正评估时，我会选一组实际列表和详情，记录传输大小、首屏图片时间、放大后的可读性，以及弱网下的占位表现。这些是后续验证建议，不是本文已经完成的测试。

从需求表达的角度，“列表足够清楚，点开能看细节”比“全部使用最高质量”更接近真实体验。语义档位提供的价值，是让产品意图与技术策略之间有一个稳定的接点。
