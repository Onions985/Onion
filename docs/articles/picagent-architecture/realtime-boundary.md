## 业务到底想“发送”什么

当聊天、评论、关注和生成任务都需要推送时，很容易让业务服务直接拼 MQTT topic、序列化消息并操作连接。第一次这样写通常很快，后来每个业务都开始知道传输协议的细节。

PicAgent 这次调整把传输能力放进 `agent-realtime`，业务通过明确的接口发送事件。它仍然使用 MQTT，并没有因为出现接口就自动拥有 WebSocket 实现。这里真正改变的是依赖方向：业务表达发送意图，适配器负责把意图转换为当前传输行为。

## 两种发送承诺不能藏在一个方法名里

实际接口保留了两个操作：

```kotlin
interface RealtimePublisher {
    fun publishBestEffort(request: RealtimePublishRequest)
    fun publishConfirmed(request: RealtimePublishRequest, timeoutMillis: Long)
}
```

这里省略了原文件注释，方法签名保持原样。第一种用于尽力通知：序列化或传输失败不能改变已经提交的业务结果。第二种在调用方预算内等待传输确认，失败交给既有 Outbox 处理。

它们的差别不是“一个快，一个慢”，而是失败归属不同。如果普通提示的发送失败可以反过来让一笔已经提交的业务返回失败，用户会看到难以解释的状态。反过来，如果需要可靠投递的 Outbox 把异常吞掉，又会过早确认消息已经处理。

接口因此需要暴露承诺，而不只是暴露动作。

## 传输确认距离用户收到还有一段路

`publishConfirmed` 的确认只表示传输端接受发布，不代表设备已经接收，更不代表用户阅读。这个限制写在源码接口注释里，非常值得保留在业务讨论中。

可以把一次消息经过的事实分开看：数据库提交、Outbox 待发送、传输端接受、设备收到、页面展示、用户已读。它们是不同证据，不应由一个“发送成功”统一代替。

如果产品真的需要送达或已读状态，应当另外设计对应回执、消息身份和恢复路径。不能因为 MQTT 层给了确认，就在页面上显示一个更强的用户承诺。

## 连接参数也是服务端契约的一部分

会话适配器返回协议、端点、用户主体、凭证、订阅集合和有效期。客户端因此消费一个完整的会话描述，而不必在多个地方自己拼接服务器事实。

`MqttRealtimeSessionProvider` 对流集合的处理很明确：

```kotlin
val orderedStreams = when (streams) {
    LEGACY_CHAT_STREAMS -> listOf(RealtimeStream.USER_CHAT)
    CLIENT_REALTIME_STREAMS -> listOf(RealtimeStream.USER_PUSH, RealtimeStream.USER_CHAT)
    else -> throw IllegalArgumentException("不支持的MQTT实时流组合")
}
```

这里不是开放的任意 topic 订阅器。服务端只接受已经定义的组合，再根据用户身份生成订阅目标和对应凭证。固定组合同时限定了权限范围，也使旧聊天会话与新组合会话的兼容关系更容易说明。

部署时还需要核对凭证在 Broker 中的验证方式，以及凭证过期后的恢复行为。

## 有意义的抽象，应当减少业务必须知道的事

我认为一个抽象是否有效，可以观察调用方还需要问哪些问题。评论服务需要知道“向谁通知、什么事件”，但不该知道 Broker 地址、具体 topic 拼接规则、连接如何回收。Outbox 需要知道确认和超时，却不应该假装可以保证用户读到了。

这类接口也不宜过早扩展成支持所有消息平台的万能框架。当前只有 MQTT，就先把真实的 MQTT 行为和业务承诺分开。未来增加另一种传输时，再验证它是否能兑现相同接口，而不是把差异都藏进适配器。

## 写需求时可以直接追问的三件事

第一，断线以后从哪里恢复业务事实？单纯推送通常不能替代权威查询。第二，重复通知依靠什么身份合并？传输层重发不应导致业务重复执行。第三，发送失败影响谁：当前操作、后台投递任务，还是仅影响即时提示？

这些问题能够让“加一个实时推送”从一句模糊要求变成可讨论的行为。它们是从代码边界得到的设计建议，并不表示此提交已经替每个业务完成了全部恢复机制。
