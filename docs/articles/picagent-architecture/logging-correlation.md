## 多一个进程，定位问题就多一次猜测

当请求经过网关再到业务服务时，“服务器报错了”已经不够具体。需要知道请求在哪一层结束、是否到达下游，以及同一条链路在不同日志里对应哪几条记录。

PicAgent 这次整理抽出了 `agent-logging`，统一结构化事件、字段策略和日志文件组织，同时保留业务线程池与协程装配在主服务。目标不是让每个模块打印更多内容，而是让有限的信息能够准确关联。

## traceId 和 requestId 解决不同的问题

这一实现用 `X-Trace-Id` 沿请求链路传播关联身份，每个服务再生成自己的 `requestId`。这样既能串起跨服务请求，也能区分每个服务的处理过程。

它是请求关联机制，不是完整的分布式 span 系统。仅仅有一个相同字符串，还不能得到父子 span、采样和精确的跨服务时序。给能力取一个准确的名字，能防止后续把工具没有提供的结论当作事实。

来源不可信的关联头也不能直接写进日志。实际策略如下：

```kotlin
private val SAFE_TRACE = Regex("[A-Za-z0-9._-]{1,64}")

fun resolve(values: List<String>): String =
    values.singleOrNull()?.takeIf(SAFE_TRACE::matches) ?: newId()
```

这里摘录了同一文件中的两处定义。只有一个值且满足字符、长度限制时才保留，否则生成新值。重复头不随意选一个，避免代理与应用各取不同值，使一次请求出现两条相互矛盾的身份链路。

## 线程复用让“清理”成为正确性问题

Servlet 路径里，外层过滤器为请求安装上下文，处理结束后在 `finally` 恢复原 MDC。异步和错误分派沿用请求身份，再按各次线程执行安装与清理。

恢复原上下文与简单清空并不完全一样：调用链可能还有外层已经建立的环境，不能把它一起擦掉。线程会被复用，遗漏清理则可能让后一个请求继承前一个请求的身份。

网关使用 Reactor，不能把 ThreadLocal 当成整个异步请求的永久存储。该版本把 trace 放进 exchange attribute，记录日志时才进入短作用域 MDC。这些细节决定日志能否可信，往往比日志格式是否整齐更重要。

## 记录完成事件之前，先确认真的完成了什么

异步请求刚交出线程时，响应状态可能还是默认的 200。如果此时记录完成，会把后续超时或失败写成成功。

目录服务因此在异步完成回调中记录最终状态，并用请求内的原子标记避免多次记录。网关取消则使用明确的取消阶段；状态 0 只在该事件的取消组合下成立，不能泛化成普通 HTTP 状态。

还有一个容易混淆的边界：访问日志表示 HTTP 处理结果，不保证业务内部所有动作都成功。业务失败仍可能有自己的响应外壳与错误码，需要独立解释。

## 不记录什么，也是日志设计的一部分

这轮整理删除了通用请求正文记录，避免 body、query、凭据与任意路径变量被顺手输出。认证失败使用受控原因，异常保留必要类型和定位信息。

字符串脱敏可以作为补充，却不能证明任意自由文本都安全。最可靠的第一步是减少输入：结构化事件只接受需要的字段，让日志代码不拿到完整对象和用户正文。

服务名、实例名与环境也会进入文件路径和 JSON，因此同样需要验证。日志按服务与实例分目录，避免多个进程争抢一个滚动文件；容量与保留策略则仍要按实际部署评估。

## 我希望日志能回答的问题

一个失败请求至少应该能回答：进入了哪个服务？用了哪条路由？最后在哪个阶段结束？大约耗时多久？失败类型是什么？是否有对应下游记录？

这些问题通常不需要用户正文。让日志承担诊断责任，同时限制它收集的数据，是比“先把全部对象打出来，以后再删”更可持续的做法。
