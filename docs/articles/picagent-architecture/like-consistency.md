## 一个点赞按钮，背后至少有两种事实

用户关心“我是否点过赞”，作品关心“总共有多少赞”。前者是关系，后者是聚合。它们在页面上挨得很近，存储和更新路径却可能不同。

如果关系写 MySQL、计数先写 Redis，再依靠任务同步，系统就需要解释很多中间状态：缓存丢失怎么办，同步失败怎么办，刚取消的赞为什么还在，旧任务能否覆盖新结果。

PicAgent 这次修复把关系与计数收回同一个数据库事务。Redis 仍参与核对提示，但不再承担业务事实的持久性。这是一次明确的权威来源调整，而不只是给计数加一把锁。

## 先锁作品，再判断关系

`LikePersistenceService` 使用短事务，隔离级别为 READ_COMMITTED，传播方式为 REQUIRES_NEW。实际操作先锁定有效作品，再读取当前用户关系，随后写入关系、按真实关系重算计数。

其中几个关键行是：

```kotlin
val liked = relationMapper.hasUserLikedWork(request.userId, workId) == 1
val nextLiked = targetLiked ?: !liked
```

以及关系写入后的：

```kotlin
check(changed == 1) { "点赞关系写入行数异常: workId=$workId" }
val count = workLikeMapper.countRelations(workId)
workLikeMapper.updateLikeCount(workId, count)
```

这是同一个方法中的两个摘录，完整方法还包含作品行锁、重复操作判断和返回值。顺序很重要：toggle 必须在锁内基于当前状态决定下一状态；如果先读后锁，两个请求可能根据同一份旧关系作出相同决策。

计数使用真实关系重算，减少“加减次数”与“实际存在关系”之间的漂移空间。它也有成本：热门作品的行锁与关系计数可能成为负载点，需要后续测量，不能仅凭一致性更清楚就声称吞吐量提高。

## 幂等目标与 toggle 不是一回事

“设为已点赞”表达目标状态，“切换一次”表达一次动作。重复发送后者，会再切换一次；它天然不能因为接口名叫点赞就被当作幂等操作。

该版本对明确 like/unlike 的重复请求保留既有 400 行为。这意味着重复请求不会被悄悄当作新变化，但也不是所有重复调用都返回成功。客户端需要按实际接口语义处理，而不是假设重试没有任何副作用。

如果发生提交结果未知，先查询当前状态再决定下一步，比盲目再次 toggle 更合理。用户表达的是希望得到某种结果，网络层重放的却可能是一个会反转结果的动作。

## 核对任务不能删掉新变化留下的线索

Redis 的变化集合增加了每作品 revision。登记时写入新 UUID，任务拿快照完成数据库核对和缓存清理以后，只有 revision 仍相同才确认删除。

设想任务读到版本 A，处理期间又发生一次点赞，登记变成 B。任务完成 A 后若直接移除集合成员，就把 B 的核对机会一起抹掉。比较 revision 的作用，就是让旧任务只能确认自己处理过的那一代变化。

异常时不能确认；数据库查询失败也不能被解释成作品不存在。Redis 提示全部丢失时，仍有按数据库游标执行的全量核对作为另一条恢复路径。

## 读取也要避免拼出不一致快照

只修写入还不够。如果页面分别查询总数和个人关系，两次查询之间发生变化，仍可能组装出互相矛盾的状态。

该修复让批量读取在同一条查询中取得作品计数与个人关系；列表、详情即使命中旧缓存，也在返回前用数据库结果覆盖点赞字段。缓存继续服务它擅长的读取加速，权威判断则回到明确的位置。

## 上线边界是设计的一部分

旧版本的 Redis 到数据库同步任务不能与新版本并行写入同一计数，否则新事务刚建立的事实还可能被旧任务覆盖。历史设计明确要求停止全部旧实例后切换。

修复代码也不等于历史聚合已经全部恢复。首次完整核对前，存量计数仍可能不准确。这个区别应该写进发布说明，而不是留给用户在页面上发现。
