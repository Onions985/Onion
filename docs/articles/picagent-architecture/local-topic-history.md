## 一句“结束后还能看”，需要先补全条件

话题到期或房主提前结束后，云端聊天内容会被清除。用户仍然能读取当前账号在当前设备上已经保存的记录，但不能据此推导出“换设备也能恢复”或“结束前没下载的消息还能补齐”。

这是 PicAgent 这一阶段明确的产品边界。它对技术设计的影响很大：本地数据库不再只是加速网络列表的缓存，而是云端结束以后仍然存在的一份历史。

一旦承诺不同，保存时机、账号隔离和备份策略都要跟着改变。

## 持续保存，比结束时抢救更可信

如果只在房间关闭时下载历史，就需要赌设备在线、进程存活、关闭通知及时，而且云端数据还没有被清理。每个条件都可能不成立。

该设计选择持续保存已经获得的消息与相关状态。结束后展示的是此前确实落在本机的数据，不发起一轮“最后抢救同步”并假装总能完整恢复。

因此，本机记录页必须说明范围：它不是完整云端档案，更不是另一份服务器会话列表。没有收到的数据不会因为页面标题叫历史，就自动存在于数据库里。

## 账号要进入数据身份，而不只是页面筛选

Room 的房间实体使用复合主键，源码定义为：

```kotlin
@Entity(tableName = "topic_room", primaryKeys = ["accountId", "roomId"], indices = [Index(value = ["accountId", "lastActivityAt"])])
internal data class TopicRoomEntity(
    val accountId: Long,
    val roomId: Long,
    val lastActivityAt: Long,
    val payload: String,
)
```

消息身份进一步包含 `accountId + roomId + messageId`，关联外键也保留账号。这样即使两个账号访问过同一个房间，它们在当前设备上的保存范围与权限状态也不会被揉成一份。

只在界面查询时加 accountId 还不够，迟到的网络响应仍可能在切号后写入错误会话。设计因此还要求 session fence：持久化前后核对操作所属账号会话，失效结果不能继续发布状态或提交去重记录。

## 消息、游标和摘要要一起考虑

本地模型不仅有正文，还包括同步快照、轮次、pending 和创建尝试。游标与已保存消息需要保持一致，否则进程中断后可能出现“游标已前进，消息没落库”的缺口。

轮次独立于正文也有业务理由：一次轮次可能没有产生回复，但仍有可展示的费用或结算信息。若强行让它依附消息行，零回复情况就失去了表达位置。

创建票据与正式房间分开，则避免失败草稿被查询成“已经加入的话题”。这些表的意义来自真实状态区别，并不是为了预留一个通用聊天平台。

## 离开、解散与暂时查不到，是三种状态

普通成员退出只撤销自己的云访问，不代表房间对其他成员已经解散。本地已存记录保留，但不能继续拉取、发送或靠推送恢复云权限。

同样，列表某一页没有出现房间、一次网络超时，都不能作为解散证据。设计使用已知房间的权威结果、合法终态通知与满足条件的校准截止时间，明确什么时候可以关闭云操作。

终态墓碑还承担另一个作用：即使某次关闭通知先于房间正文到达，也能阻止后续旧响应把访问重新打开。这类状态必须解释“防止哪一种逆转”，才值得持久化。

## “仅本机”也包括系统备份边界

需求既然明确仅当前设备，就不能默认允许数据库随系统云备份或设备迁移出去。该实现为独立话题数据库及其附属文件配置精确排除，同时保留其他备份范围。

这只是本功能的恢复范围设计，不代表数据库本身已经获得额外加密，也不应该推广成对整台设备隐私能力的保证。

我认为这类需求最需要的是准确文案：告诉用户保留了什么、丢失了什么、在哪里还能看到。数据结构、生命周期和页面提示共同兑现一个有限但可信的承诺。
