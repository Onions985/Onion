## 用户确认的究竟是什么

“是否继续？”几乎可以放在任何按钮后面，却很少解释继续会发生什么。在 Storyline 安装场景里，真正需要说明的是角色会永久冻结，之后不能修改或删除。

如果对话框只重复“安装”，用户确认的是动作名称，而不是不可逆后果。需求设计因此应该先写清后果，再决定标题、按钮和视觉强度，而不是先规定“这里加个弹窗”。

## 确认应当绑定一份具体条件

弹窗打开时，用户看到的是某个账号、角色、商品、价格与安装能力。等待确认期间，这些信息可能改变。

该实现没有只保存 `showDialog=true`，而是在 ViewModel 状态中保存确切的待安装 item。确认时再次检查当前账号归属、绑定代次以及 item 是否仍然匹配且允许安装。

保存完整目标比只保存 appKey 更有意义：同一个 appKey 的价格或能力发生变化后，旧确认不应自动适用于新条件。用户同意的是刚才被告知的操作，而不是任意后续版本。

## 点了确认，才产生接受对象

真正提交时使用 KMP 定义的确认类型：

```kotlin
CharacterWorldStorylineFreezeConfirmation(
    accepted = true,
    policyVersion = CharacterWorldStorylineFreezePolicy.VERSION,
)
```

这段摘录来自 `confirmStorylineInstall`。策略版本使用共享常量，Android 不另外写一个数字或手工 JSON map。确认信息因此成为请求契约的一部分，而不只是界面上短暂出现过的状态。

但客户端对象也不是后端校验的替代品。旧客户端、直接调用和过期策略都可能绕开 UI，服务端仍需要决定这个确认是否有效，以及是否允许发生冻结与扣费。

## 取消必须有可以验证的含义

取消按钮、系统返回和点击外部，都只清除待确认目标，不创建安装请求。源码里的 `dismissStorylineInstall` 就只更新本地状态。

这是很具体的验收标准：取消之后请求数量应该为零。相比“取消体验正常”，它更容易定位错误。弹窗展示不能算同意，默认勾选不能代替明确动作，重组也不能触发提交。

确认回调先清掉待确认目标，再继续提交，配合提交中状态与任务检查，防止同一个决策点被反复消费。

## 网络重试与重新同意可以同时存在

如果请求结果未知，不能为了重试就生成一个新付款身份。这一流程保留稳定 UUID；用户下次主动操作时重新经过明确确认，再用原身份恢复或重放。

看起来似乎重复，但两者解决不同的问题：用户确认表达此刻仍愿意继续，稳定请求身份保证服务器能够识别此前可能已经提交的同一动作。

若服务器明确拒绝确认，流程回到决策点；若已经确认业务提交，后续布局恢复有问题，则走权威查询，不应再次扣费。把所有失败压成一个“再试一次”，会丢失这些关键区别。

## 我会怎样写这种需求的验收

除了正常确认，还需要描述条件漂移：弹窗期间切号、切角色、价格更新、商品不再可安装，旧决策都应失效。网络结果未知时，需要观察请求身份是否保持。取消、返回、外部关闭则都不能发请求。

这些不是额外的工程洁癖，而是“用户同意这一次操作”本身包含的条件。界面再精致，如果把 A 账号的确认应用到 B 账号，就已经改变了用户的意思。

我更愿意把确认框看成一个短暂的决策合同：告诉用户后果，固定相关条件，接受一次明确动作，条件改变就重新询问。它应该出现在真正需要决定的地方，也应该足够具体，让用户知道自己在决定什么。
