## 介绍面板之前，先确认用户处在哪一步

给新功能加一张介绍图很容易，难的是判断什么时候应该展示。用户已经创建过 AI 分身时，再把他带进创建介绍，会让产品显得不认识自己的数据。

PicAgent 这个版本的入口先查询角色类型与当前用户角色，再决定进入已有分身或展示创建介绍。引导不是单纯依靠本地“看过一次”的布尔值，而是围绕当前业务状态作出选择。

这种判断的意义在于：用户换设备、重装或状态发生变化以后，入口仍然有机会回到真实业务事实，而不是沿用一份已经失去语境的本地标记。

## 查不到，不等于没有

`resolveAiTwinEntry` 同时需要类型字典和用户角色。任一结果缺失，或者无法识别 AI 分身类型，就回到空闲并按已有反馈规则处理，而不是把失败解释为“尚未创建”。

这个边界直接影响用户行为。如果网络失败被包装成创建引导，用户可能重复创建，或者误以为原来的分身丢了。一个看似积极的空态，反而制造了错误判断。

“暂无内容”应该来自成功查询后的业务结论，“目前无法确认”则需要自己的恢复路径。它们可以共用一些视觉组件，但不能共用同一套事实。

## 引导组件只承担解释和选择

介绍面板的接口很克制：

```kotlin
internal fun MyAiTwinIntroSheet(
    show: Boolean,
    avatarUrl: String?,
    onCreateClick: () -> Unit,
    onDismiss: () -> Unit,
    modifier: Modifier = Modifier,
)
```

这是函数签名摘录，原函数还带有 Compose 注解和实现。面板接收展示状态、头像与两个操作，不在内部查询角色或发起创建请求。

它可以解释“AI 分身与我有什么关系”，用当前头像和数字身份图形帮助理解，再让用户选择创建或稍后。关闭只收起面板，确认之后才由调用方进入创建页。

这种边界让展示代码不必掌握业务数据，也让入口逻辑能明确判断哪一个用户动作触发了导航。

## 用户已经关掉了，旧请求就不应该重新打开

网络响应会晚到，界面状态也可能延迟提交。该入口维护请求代次，并核对当前账号。关闭入口时会递增代次，使仍在执行的旧请求失效。

源码中的判断是：

```kotlin
return requestId == aiTwinEntryRequestId &&
    userDataStore.getUserFlow().first()?.id == ownerUserId
```

这一检查也出现在延迟发射状态之前，而不只放在 HTTP 返回之后。否则在“检查通过”和“状态真正显示”之间切号，旧结果仍可能出现在新账号页面。

从体验角度看，这其实是在尊重关闭动作：用户已经说了暂时不看，系统不应因为一条旧响应又把介绍推回来。

## 引导不是把所有功能解释一遍

我倾向于让首屏介绍只回答三件事：这是什么、与我有什么关系、下一步会发生什么。具体配置和高级能力可以留在真正使用时逐步解释。

这份代码中的头像与分身图形是一种关系表达，而不是展示系统内部工作流程。用户需要理解将要创建的身份，不需要在入口学习 Repository、任务状态或模型参数。

“稍后”也应该是完整选择，而不是视觉上几乎找不到的退出通道。这里不需要推导出某种转化率提升；代码和设计本身没有提供用户实验数据，能确认的是操作分工与状态边界。

## 判断引导是否有效，别只看它是否漂亮

我会先检查已有用户能否直接进入、查询失败会不会误导创建、重复点击是否产生多个流程、关闭以后是否还会被旧请求拉回，以及切号后是否展示了正确身份。

这些条件成立以后，插画、字号和间距才有稳定的基础。好的首次使用体验，不是每次都热情介绍，而是在合适的时候给出刚好足够的信息。
