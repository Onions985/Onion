## “都在上传文件”不代表属于同一层

头像、生成媒体和客户端直传都需要对象存储。最初把相关代码放在业务服务里很自然；随着入口增加，签名、元数据检查、资源关闭和错误转换就开始重复。

但把这些代码全部移动到一个公共模块，也可能把用户权限、业务状态和数据库事务一起搬过去，得到一个依赖更多的“大公共服务”。PicAgent 这次选择把技术操作收拢到 `agent-storage`，让业务决策继续留在主服务。

## 一个普通 JAR 足够解决当前问题

`agent-foundation` 是构建聚合，`agent-storage` 是进程内普通库。它不独立启动、不注册服务发现，也没有自己的 HTTP 上传入口。

这个选择很实际：当前痛点是重复能力和依赖散落，不是上传进程必须独立扩容。增加网络服务会引入另一套鉴权、超时和部署问题，未必能解决眼前的重复代码。

这并不排除以后拆成服务。只是当前的可复用边界先体现在代码依赖上，不必立刻体现在网络拓扑上。

## 库负责对象事实，业务负责对象意义

在这个提交中，公共能力负责上传、签名、HEAD 元数据、ACL 校验、图片技术检查和媒体处理协议。业务则决定对象 key、用途、可见性、期限、尺寸门限，以及文件何时真正绑定到内容。

例如，某个对象存在且大小、类型都正确，只能说明它在技术上符合上传预期，不能说明当前用户有权把它绑定为某个角色的头像。

同理，对象上传完成也不等于业务成功。上传归属、数据库记录、READY/BOUND 状态、事务绑定和清理资格仍由主服务掌握。这样的边界让公共库不必理解“角色”“作品”或“钱包”，业务也不必知道 SDK 细节。

## 用作用域表达资源生命周期

底层接口有一个值得注意的签名：

```kotlin
interface ObjectStorage {
    fun <T> execute(timeoutMs: Long? = null, action: (ObjectStorageOperations) -> T): T
}
```

方法在一个有界作用域中提供操作能力。该版本每次调用创建、关闭客户端，作用域内部可以复用多个操作，`operations` 及其资源不能逃逸出去。

它并不是连接池，也没有承诺长期复用 SDK 客户端。好处是生命周期有清楚的入口和出口；代价是客户端创建成本需要在真实负载下评估。文章不能只因为接口简洁，就顺带推导出性能更高。

`timeoutMs` 同样有具体含义：在旧上传模式中传递剩余请求预算，空值保留原有默认行为。兼容参数应当说明它服务于什么约束，避免未来被误当作所有模式统一的超时配置。

## 公共实现也要保留不同模式的差异

这里同时存在旧上传模式和 V4 直传模式。它们的签名方式、超时与错误行为并不完全一样。抽取时没有把差异强行压成一个默认值，而是通过具名客户端和明确的模式保持原有边界。

自动配置只装配能力；它不会在应用启动时访问 OSS、校验 bucket 或创建 SDK 客户端。直传关闭、相关参数尚未配置时，依赖这个库本身不应让无关应用启动失败。

网关和目录服务也不会因为使用基础模块就自动获得 OSS 依赖。公共模块应该按需引入，而不是变成所有应用共享的一包运行依赖。

## 错误抽象比方法抽象更容易遗漏

厂商异常往往携带动态请求信息。如果公共库直接把它们一路传到用户侧，就会让页面、日志和业务代码都依赖供应商细节。

该版本在直传边界提供固定失败原因，由业务映射既有响应。与此同时，旧接口原有的异常传播范围需要保持，不能为了“统一风格”悄悄吞掉以前会被调用方处理的异常。

我更愿意用一张责任表审视这种抽取：谁能决定删除？谁决定公开？谁解释失败？谁负责事务回滚？如果答案仍然清楚，移动文件才算改善了架构，而不只是缩短了某个目录。
